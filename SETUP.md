# Profile Repository — Setup Guide

This repo is a **GitHub profile repository**: a repository named exactly the same as your
GitHub username (e.g. `your-username/your-username`). GitHub automatically renders its
`README.md` at the top of your profile page.

## 1. File / folder structure

```
your-username/
├── README.md                          # The profile page itself
├── SETUP.md                           # This file
├── .github/
│   └── workflows/
│       └── profile-stats.yml          # Regenerates the stats SVGs on a schedule
├── scripts/
│   └── generate-stats.mjs             # Node script that builds the SVG cards
└── profile/
    ├── stats.svg                      # Generated — commits/PRs/issues/stars/followers
    └── top-langs.svg                  # Generated — top languages by bytes
```

## 2. Exact setup steps

1. Create a repository named exactly `your-username` (replace with your real GitHub
   username) — GitHub will show a banner offering to do this automatically the first
   time you create a repo matching your username.
2. Copy every file in this delivery into that repository, preserving the folder
   structure above.
3. Find-and-replace every `your-username` placeholder in `README.md` (repository links,
   the contribution-graph URL, footer links) with your actual GitHub username.
4. Replace the LinkedIn, Portfolio, and Publication placeholder URLs in `README.md`
   with your real links. Do **not** invent a publication URL — use the actual
   IEEE Xplore / DOI link for the research paper.
5. Commit and push to `main`.
6. Go to **Settings → Actions → General → Workflow permissions** and confirm
   "Read and write permissions" is enabled for the default `GITHUB_TOKEN` (required
   for the workflow to commit the generated SVGs back to the repo).
7. Go to the **Actions** tab, select **Update profile stats**, and click
   **Run workflow** once manually. This generates the first real `stats.svg` and
   `top-langs.svg` (the versions committed in this delivery are zero-value
   placeholders so the README never shows a broken image, even before the first run).
8. Reload your profile page — the stats cards and contribution graph should now be live.

No secrets need to be created for the default setup — the workflow uses the
automatically-provided `GITHUB_TOKEN`, which is sufficient to read public profile data
(contributions, public repos, languages, followers, stars).

## 3. How "GitHub Activity" works

Three visuals make up the section, and they're generated by two different, deliberately
separated mechanisms:

- **`profile/stats.svg` and `profile/top-langs.svg`** — generated locally, inside this
  repository, by `scripts/generate-stats.mjs`, which calls the GitHub REST and GraphQL
  APIs directly with Node's built-in `fetch` (no third-party npm packages). The
  `.github/workflows/profile-stats.yml` workflow runs this script daily and on manual
  dispatch, then commits the two SVG files back to `profile/` if anything changed. The
  README embeds them as local, repository-relative image paths
  (`./profile/stats.svg`), so they render from GitHub's own asset CDN — the same
  infrastructure that serves the README itself — rather than a third-party endpoint.
  This is what avoids the reliability problem with public instances of tools like
  `github-readme-stats`: there is no external service in the critical path, and no
  rate limit shared with other users.
- **Contribution activity graph** — embedded from the currently maintained
  `github-readme-activity-graph.vercel.app` deployment, per your instructions, since a
  fully faithful heatmap-style contribution graph is impractical to hand-roll reliably
  as a static asset in a lean workflow. If this dependency is ever unavailable, delete
  the `<img>` line for it in `README.md` rather than leaving a broken image — the two
  self-hosted cards above are unaffected either way.

### Why not the public `github-readme-stats` Vercel endpoint?

Its own documentation notes the shared public instance is best-effort and can be
affected by rate limits, and recommends generating cards via GitHub Actions/static
assets for reliability — which is exactly what `stats.svg` and `top-langs.svg` do here.

### Why not `lowlighter/metrics`?

It's a capable all-in-one metrics action, but the upstream project has had long gaps
between releases and known-broken plugins tied to deprecated GitHub APIs. A small,
self-contained script gives you full control over exactly two cards, with no plugin
surface that can silently break.

## 4. Avoiding broken images going forward

- The workflow commits `profile/stats.svg` and `profile/top-langs.svg` as real files in
  the repo, so they render even if GitHub Actions is temporarily unavailable — the
  README always points at the last successfully generated version.
- The workflow uses `workflow_dispatch` (manual trigger) and a daily `schedule`, and
  skips the commit step entirely when nothing changed, so it never produces empty
  commits.
- If `scripts/generate-stats.mjs` ever fails (for example, a GitHub API outage), the
  workflow run fails but the previously committed SVGs remain in place — the README
  never shows a broken image, only a stale one.
- The only non-self-hosted image is the contribution-graph `<img>` from
  `github-readme-activity-graph.vercel.app`. If that specific dependency degrades, it's
  a single line to delete from `README.md`.

## 5. Visual rationale

- **Typography over decoration** — the entire page uses GitHub's default markdown type
  scale plus monospace for numbers/labels/technical metadata. No banner image, no
  animated GIFs, no progress bars.
- **One accent color** — a single blue/cyan (`#58a6ff`, GitHub's own dark-theme link
  color) is reused across the SVG cards and nowhere else, so it reads as an intentional
  system rather than decoration.
- **Numbered system, not a list** — `01`–`06` recur across Engineering Focus and both
  project sections, giving the page one consistent way of establishing hierarchy
  instead of icons, emoji, or badges doing that job inconsistently.
- **Selected Work is the centerpiece** — the three flagship projects get full
  description + signals + tech + repo link; the other three get a compact three-column
  grid instead of matching height, so the page doesn't flatten every project to the
  same visual weight.
- **Tech logos, not a badge wall** — the Technology Stack table keeps the
  category/logo-row format, using real per-technology logos (via shields.io's
  simple-icons integration) rather than decorative status badges (build passing,
  license, etc.), which the spec explicitly asked to avoid.
- **Dense but not cramped** — one blank line between sections, no section headers
  repeated in oversized banner text, so the whole profile is scannable in a single
  scroll on both desktop and mobile.
